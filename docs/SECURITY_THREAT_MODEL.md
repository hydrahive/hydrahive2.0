# HydraHive security threat model

> **Scope:** current repository and default Linux deployment
> **Validated:** 2026-09-06
> **Reporting:** [SECURITY.md](../SECURITY.md)

This document describes assets, trust boundaries and implemented controls. It is not a certification, penetration-test result or guarantee of security.

## 1. Protected assets

- user identities, password hashes, JWTs and API keys;
- provider keys, OAuth tokens, SSH keys and service credentials;
- chats, memory, prompts, attachments and generated media;
- project workspaces, repositories, tasks and source code;
- medical, health, finance and portfolio records;
- server, VM, container and compute-node control channels;
- system update, migration and extension-install privileges;
- audit records and backups.

## 2. Trust zones

```text
Untrusted/less trusted
  Browser input · uploaded files · web content · model output
  external providers · MCP servers · messaging networks
  third-party modules/plugins/extensions
          │
          ▼
Edge
  nginx TLS/static/API proxy · upload limits · security headers
          │
          ▼
Application trust zone
  FastAPI · auth/ownership checks · runner · tool dispatcher
          │
          ├── User data zone: SQLite, files, encrypted credentials
          ├── Project zone: workspaces, repositories, mounts
          ├── Privileged host zone: sudo extension actions, VM/container control
          └── Remote zone: mTLS compute nodes, federation, explicit outbound SSH operations
```

Administrators and locally installed executable packages are privileged actors. AI model output is never inherently trusted, even when produced inside the application.

## 3. Entry points

- login, API-key and OAuth endpoints;
- REST API under `/api`;
- SSE chat streams and WebSocket endpoints;
- file, image, audio, video and ISO uploads;
- inbound WhatsApp, Discord, Matrix, mail and health-data traffic;
- remote compute-node/federation connections and explicit SSH-backed tool or migration operations;
- module/theme/plugin package installation;
- privileged service-extension installers;
- prompts and tool arguments generated by models;
- Vault launchpad routes leading to sensitive application areas.

Core route registration can be reviewed in `core/src/hydrahive/api/main.py`; runtime module routes are added by `core/src/hydrahive/modules/loader.py`.

## 4. Main threats and controls

### 4.1 Account compromise

**Threats:** password guessing, stolen JWT/API key, stale authorization after role changes, deleting/recreating a username to inherit resources.

**Implemented controls:**

- bcrypt password hashes;
- lazy migration of legacy SHA-256 hashes;
- expiring JWTs;
- API-key verification;
- immutable user IDs for newer owned resources;
- resolution of current user and role for principal-based authorization;
- final-administrator demotion protection;
- in-memory login lockout/throttling keyed by username and client IP.

**Residual risk:** bearer credentials work for whoever possesses them. Not every legacy route may use the newest immutable-principal dependency; authorization regressions require continuous tests and review.

**Sources:** `core/src/hydrahive/api/middleware/auth.py`, `api/middleware/users.py`, `api/middleware/lockout.py`, `api/routes/auth.py`.

### 4.2 Cross-user or cross-project access

**Threats:** insecure direct object reference, username collision, path traversal, trusting a client-supplied project ID.

**Implemented controls:**

- user ownership checks on sessions and resources;
- project membership and role helpers;
- stable user IDs;
- workspace path resolution and file-operation validation;
- scoped tool context containing user/project identity.

**Residual risk:** HydraHive has a large API surface. Any new route that bypasses centralized checks can reintroduce cross-tenant access. Mounted files and intentionally powerful shell/server tools broaden the reachable filesystem.

**Sources:** `core/src/hydrahive/api/routes/_project_route_helpers.py`, `projects/members.py`, `runner/_run_workspace.py`, `api/routes/_files.py`, route tests under `core/tests/`.

### 4.3 Shared data-mining visibility

**Threats:** an authenticated user searches another user's mirrored events or obtains aggregate data beyond their normal session ownership.

**Implemented controls:** the API requires authentication, keeps credential values out of mirrored event payloads by design and exposes explicit analytics endpoints rather than arbitrary SQL.

**Residual risk:** current data-mining routes are not a strict per-user authorization boundary. Several endpoints query globally, and some accept an optional username filter. On mutually untrusted multi-user deployments, restrict/disable this surface until fine-grained ownership enforcement exists.

**Sources:** `core/src/hydrahive/api/routes/datamining*.py`, `db/_mirror_*.py`, `tools/datamining*.py`.

### 4.4 Credential disclosure or misuse

**Threats:** secrets at rest, secrets returned to a model, credential injection to the wrong host, logs containing tokens.

**Implemented controls:**

- AES-GCM encryption of stored credential values;
- per-user credential files with mode `0600` where supported;
- URL/host-pattern matching;
- server-side injection into HTTP/Git/shell-related operations;
- masked UI responses;
- explicit credential-profile and URL/host selection.

**Residual risk:** the application must decrypt a secret to use it. A compromised backend/admin account or malicious authorized tool can still misuse credentials. Over-broad URL patterns increase exposure.

**Sources:** `core/src/hydrahive/credentials/`, `tools/fetch_url.py`, `tools/shell_exec.py`, `plugins/context.py`, `plugins/tool_bridge.py`.

### 4.5 Prompt injection and unsafe tool use

**Threats:** untrusted documents or websites instruct a model to exfiltrate data, modify files, send messages or install software.

**Implemented controls:**

- per-agent tool allowlists;
- permission checks in tool schemas/dispatch;
- optional confirmation gate;
- explicit tool-call display in chat;
- loop and iteration limits;
- output compression and validation.

**Residual risk:** prompt injection cannot be solved only by a system prompt. If a user assigns a powerful tool and approves the call, the action can occur. Tool confirmation should be enabled for high-impact agents, and displayed parameters must be reviewed.

**Sources:** `core/src/hydrahive/runner/_runner_tools.py`, `runner/runner.py`, `runner/_runner_iter.py`, `tools/base.py`, `tools/__init__.py`.

### 4.6 File upload and media processing

**Threats:** oversized requests, path traversal, malicious media/parser input, disk exhaustion, unsafe preview content.

**Implemented controls:**

- nginx request-size limits, including dedicated chat-upload handling;
- application-side upload validation and owned media paths;
- generated media served through controlled routes;
- security headers and restrictive CSP in the default proxy.

**Residual risk:** codecs, ffmpeg, image libraries and model workers process untrusted formats. Large but permitted files can consume storage/CPU. Infrastructure should monitor capacity and keep native dependencies updated.

**Sources:** `installer/modules/60-nginx.sh`, `core/src/hydrahive/api/routes/session_uploads.py`, `media_assets.py`, `media_workspace.py`, `runner/_media.py`.

### 4.7 Plugin and module execution

**Threats:** third-party package executes malicious Python or subprocess code, accesses application data or weakens authorization.

**Implemented controls:**

- explicit installation/activation;
- manifest validation;
- per-module and per-plugin load failure isolation;
- per-agent plugin assignment;
- explicit administrator-driven install/update/uninstall.

**Residual risk:** runtime modules and plugin entry modules execute inside the backend process. There is no process or OS sandbox between them and HydraHive. Administrators must treat both as fully trusted code.

**Sources:** `core/src/hydrahive/modules/loader.py`, `modules/installer.py`, `plugins/manifest.py`, `plugins/loader.py`, `plugins/tool_bridge.py`.

### 4.8 Privileged extension installation

**Threats:** manifest or install script obtains root access, package supply-chain compromise, destructive uninstall.

**Implemented controls:**

- extension APIs are administrator-only;
- known manifests/scripts are repository-controlled;
- install state and logs are exposed for review.

**Residual risk:** the default service sudoers configuration permits privileged shell execution for extension management. An extension script is effectively trusted root code. Admin compromise can therefore become host compromise.

**Sources:** `core/src/hydrahive/api/routes/extensions.py`, `api/routes/_extensions_*.py`, `extensions/`, `installer/modules/50-systemd.sh`.

### 4.9 Remote compute, federation and SSH operations

**Threats:** rogue node enrollment, command spoofing, stolen certificates/tokens, compromised SSH credential, node/workstation impersonation.

**Implemented controls:**

- compute CA and client certificates;
- mTLS verification on the compute connect endpoint;
- proxy secret and node identity headers;
- explicit enrollment/bootstrap flow;
- configurable TLS verification for federation workstations;
- credential-store support for explicit SSH-backed tools and migration.

**Residual risk:** a compromised enrolled node remains trusted until revoked/removed. Federation bearer tokens and explicit SSH operations cross the host boundary. Certificate/token/credential rotation and network segmentation are operator responsibilities.

**Sources:** `core/src/hydrahive/compute/`, `federation/`, `tools/shell_exec.py`, `api/routes/migration.py`, `node-agent/`, `installer/modules/60-nginx.sh`.

### 4.10 Browser attacks

**Threats:** XSS, clickjacking, content sniffing, insecure mixed content, stale frontend cache.

**Implemented controls in the default Linux proxy:**

- HTTPS redirect and HSTS;
- CSP;
- `X-Frame-Options: SAMEORIGIN`;
- `X-Content-Type-Options: nosniff`;
- referrer and permissions policies;
- immutable caching only for content-hashed assets and revalidation for HTML.

**Residual risk:** the CSP currently permits `'unsafe-inline'` styles and `'unsafe-eval'`/`'wasm-unsafe-eval'` scripts for frontend dependencies. The default self-signed certificate provides encryption after explicit trust but not public-CA identity assurance.

**Source:** `installer/modules/60-nginx.sh`.

### 4.11 External providers and integrations

**Threats:** data leaves the host, provider retention/training, third-party outage, malicious MCP result, OAuth token theft.

**Implemented controls:**

- providers are explicitly configured;
- credentials/OAuth are kept server-side;
- tools/providers are assigned per agent;
- local model paths exist for deployments that require them.

**Residual risk:** HydraHive cannot enforce a third party's privacy policy or availability. Prompts, attachments and context sent to cloud services are governed by those services. Fallback providers widen the set of possible recipients.

**Sources:** `core/src/hydrahive/llm/`, `oauth/`, `mcp/`, `tools/_openrouter_media.py`, `tools/generate_*.py`.

### 4.12 Backup, update and migration

**Threats:** backup contains plaintext user data, update supply-chain compromise, migration sends data to the wrong host, rollback loses schema/data compatibility.

**Implemented controls:**

- explicit admin backup/download and validated restore/upload APIs;
- an automatic rollback archive is created before restore replacement;
- update/restart logs plus systemd path/service helpers separate privileged lifecycle actions from normal requests;
- migration request and long-running service workflow.

**Residual risk:** many persisted chats, workspaces and media files are not individually encrypted by HydraHive. Backups must be protected at the storage/transport layer. Updates execute repository code and dependencies with substantial trust.

**Sources:** `core/src/hydrahive/api/routes/backup.py`, `system_admin.py`, `migration.py`, `backup/`, `installer/update.sh`, `installer/migrate.sh`.

## 5. Security invariants for contributors

New code must preserve these invariants:

1. Never authorize a user-owned resource by client-supplied username alone.
2. Resolve project membership before reading or mutating project data.
3. Never return credential values, tokens or private keys in API/tool output.
4. Normalize and validate filesystem paths before access.
5. Do not expose a new tool globally by accident; require explicit assignment and permission.
6. High-impact or irreversible actions must support confirmation or an equivalent explicit user decision.
7. Validate module/plugin/extension manifests before execution.
8. Do not log secrets, full authorization headers or sensitive uploaded content.
9. Preserve proxy-side and application-side upload limits.
10. Add authorization and ownership tests for every new resource endpoint.

## 6. Recommended operator hardening

- Keep the backend on loopback and expose only the reverse proxy.
- Replace the self-signed certificate with a managed certificate where appropriate.
- Restrict network access through firewall/VPN and avoid public admin exposure.
- Use a non-admin account for normal work.
- Keep tool confirmation enabled for shell, file-write, server, messaging, download and device-control agents.
- Use narrow credential URL/host patterns and rotate secrets.
- Review installed modules, plugins and extension scripts.
- Segment compute nodes and SSH-managed servers.
- Monitor disk, CPU/RAM/VRAM, failed logins and error logs.
- Encrypt and test backups; include external extension data separately.
- Review provider data-processing terms before sending sensitive material.

## 7. Out of scope for this document

This threat model does not prove:

- compliance with GDPR, HIPAA, ISO 27001 or another standard;
- safety of third-party models, services or package repositories;
- isolation against a malicious host root user;
- confidentiality when an authorized user deliberately shares data;
- complete sandboxing of plugins/modules;
- secure operation after disabling the documented proxy/auth controls.
